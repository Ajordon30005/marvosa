## What This Is (and what it is not)

The processor is a **bijective transducer** between a byte sequence and its
**HVP signature**. An HVP signature has two parts, and both are required —
this is the central correction over earlier versions:

| Part | Symbol | Role | Scales with |
|------|--------|------|-------------|
| 8 HVP parameters | L(T) | the holographic **address / grammar** | fixed (8 numbers) |
| braid word | L(D\|T) | the **data-carrying term** | the data |

The 8 parameters are a derived signature of the data's structure. The **braid
word carries the data itself**, expressed as a word in topological generators.
This matches the GUHCT theory exactly: transduction is "lossless and bijective
because there is a one-to-one mapping between the topological braid and the HCL
computational steps, **but the braid itself must be provided** as the data
source." (GUHCT source, confirmed.)

**The roles, stated precisely:** the HVP is the signature of a byte sequence of
any length, and an HVP can produce a byte sequence of any length. The 8
parameters are the holographic address/grammar of the data; the braid word is
the data-carrying term. The full HVP signature is both together, and the
transduction is bijective: `bytes ↔ (params + braid)`. This is the same
architecture as `virtual-memory-hcl`, where a topological signature addresses a
memory whose content is carried in a separate term (its Rule 6).

5. **Never invent theory.** If a derivation is unclear, query the GUHCT

## The 8 HVP Parameters (all derived, pure integer)

Each is a fixed-point integer consequence of the four params and the braid's
topological invariants. None imports a physical constant.

Stability measure (collapse readiness), from the source:

## The Pipeline

```
FORWARD   bytes_to_hvp(raw_bytes):
  bytes -> braid word (one generator per byte; exactly reversible)
        -> braid_invariants: winding number, writhe, Jones span,
           spectrum FBit (COMP accumulation), stability measure I_w
        -> forensic_reconstruct_boundary: derive the 8 HVP params
        -> return { params, braid, n_bytes }

INVERSE   hvp_to_bytes(signature, verify=True):
  braid word -> exact original bytes (braid_to_bytes)
  re-derive params from the rebuilt braid -> must match supplied params
  (mismatch => corrupt signature; match => certified bijective round trip)
```

The forward path computes the address from the data. The inverse path rebuilds
the data from the braid and uses the address as a checksum. Bijection is
verified, not assumed.

### AI speaking in HVP
An AI "speaks HVP" by emitting a full signature — the 8 parameters **and** the
braid word stream. The transcriber turns that signature back into the exact
byte sequence. The parameters are compact and fixed; the braid stream carries
the information content and grows with the data. There is no configuration in
which the braid can be omitted, because that is where the data lives.

## Format Tree — parameter-space distance between encodings

`scripts/format_tree.py` measures how far two formats sit apart in HVP
parameter space when they encode the same content:

```
offset[k]  = params_target[k] − params_source[k]      # per HVP param
severity   = √(Σ offset²)        # <0.5 trivial · 0.5–1 close · 1–3 moderate · >3 far
```

This is a **descriptive metric, not a reconstruction shortcut.** You cannot turn
source-format bytes into target-format bytes by nudging 8 numbers — the braid
(the data) differs between encodings. The tree tells you which formats are
spectrally close and which are far. Measured seed results (same text content):
`raw→json ≈ 0.19` (json just wraps the text), `raw→base64 ≈ 2.0`,
`raw→hex ≈ 6.0`, `raw→gzip ≈ 11.8` (compressed binary is farthest). The
repository log is append-only; `observe()` records the residual on top of the
current offset and re-averages, so repeated cases refine the tree.
